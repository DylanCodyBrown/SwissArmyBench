# Use Swiss Army Bench

The person's guide, with a screenshot of each feature, is
[swissarmybench-user-guide.md](swissarmybench-user-guide.md). Answer from it, and point them at the
section that covers their question.

When you are the agent working on their grids (through the swissarmybench MCP server), read its
`swissarmybench://index` resource first (or call the `guide` tool with no arguments): a short index of
the app, its tools by area and the rules. `guide(topic=...)` gives one topic in full (grids, analyze,
relationships, connections, blades, workbench, streamlit, privacy), and `agent_context` says which
table they have in front of them.

## Things people ask that the guide answers

| They ask | Point them at |
|---|---|
| Where are the settings / the theme / the agent's access? | **Settings**, first in the Application row (the top row of the ribbon, on every tab) |
| Where did the column profile go? | Select the column, then Profile on the ribbon's Column row (a popup) |
| How do I compare two tables? | Right-click a table's tab, Compare with… (or drag one tab onto another); the key picker opens with the Key Finder already run and the key unique on both sides ticked |
| Where did a table I closed go? | The ≡ button beside + in the tab strip: Tables lists the closed ones, each with Open (the same table, not a copy) |
| Where are the header profiles / the zoom? | Profiles: the small button in the grid's top-left corner, above the row numbers. Zoom: the Application row (the whole page, Analyze too) |
| How do I undo a step? / Is there a list of every command? | Ctrl+Z (Ctrl+Y redoes), or hover "N steps" under the title and remove any one. Ctrl+Shift+P lists every action of the page |
| How are my tables related? / Draw an ERD | The rail's ERD, right after Analyze: Import relationships (a saved set or a model as JSON), apply a shared model, or ask the agent to build one |
| I can't manage or mass delete my relationships | The Relationships window's **In use now**: tick rows (select all, shift-click), **Delete selected**, **Run on/off**, Kind and Run in place, filter, sort, group; **Undo** in the toast. For you: `relationships_delete`, `relationships_update`, `relationships_undo` |
| Where did the Analyze menu / Fit test / Outliers / Tie-out go? Where is Visualizations? | **Analyze** on the rail (2026-11-19): Visualizations is called Analyze, and every analysis is a button on its toolbar. A button opens one form beside the board: the table is already picked (Change), the columns are picked for you as chips, one sentence says what will run, Run. The result lands on the board by itself; under it: Show the math, Open as grid, Copy code, Run again. The grid page has no analysis on it. Old addresses (`?view=visualizations`), `sab.visualizations(...)` and the agent's `visualizations_*` names still work for one release |
| I have no data yet / Something to try / Why is the rail so wide? | Every empty page (Connections, Session, Notebooks, Scripts) has **Try it with sample data**: three made-up tables (customers, products, orders) open as grids. The rail shows its names beside the icons; **Icons only** at its foot (or right-click it) brings back the slim rail, remembered on this computer. For you: `datasets_sample`, `app_rail(labels)` |
| My table does not fit an analysis / which analysis should I run? | The form says what is missing in one sentence and **Make it fit** lists the fixes (read a text column as numbers or dates, a month column, the ten most common and Other, a yes/no column...), each with **Apply**: it is added as a step you can undo, never by itself. **Check this table** suggests the three analyses that suit the table, one click each. **What your data should look like** in a form shows a made-up sample; **Try it on this sample** runs on it |
| Where did the Sandbox / the Diagram go? | Renamed (2026-11-16): the Sandbox is **Visualizations** and the Diagram is the **ERD**, the same places on the rail. Old addresses, `sab.sandbox(...)` and the agent's `sandbox_*` commands still work for this release; write `sab.visualizations(...)` and `visualizations_*` |
| How do I read a Power BI dataset? / Bring its relationships in / Run DAX | Connections, Add connection, **Power BI workspace**: the workspace id (no dataset: one connection reaches every dataset in the workspace), and an app registration whose tenant id, client id and client secret are entries of their key vault. The catalog shows each dataset with its tables, which open as grids. DAX goes in a **DAX cell** (a cell kind of its own; its picker names a dataset as `Finance/Sales model`) or `sab.dax("Finance/Sales model", "EVALUATE ...")`. **Import its relationships**, on a dataset in the catalog, puts that dataset's joins in the ERD. For you: `connections_datasets` (a workspace's datasets), `connections_import_relationships` with `dataset`, `workbench_dax_add`, and `workbench_run` with kind `dax` and the dataset as `connection` |
| How do I read Dataverse? / Dataverse tables in a notebook / SQL on Dataverse | Connections, Add connection, **Dataverse**: the environment's address and a sign-in (an app registration whose client secret is a key vault's entry, never typed; a managed identity; or as you, which works on this computer only). Its tables are listed and read on its read-only SQL endpoint (one schema, dbo; a connection saved for the Web API has a one-click switch); `sab.read("Sales CRM", "account")` reads through the Web API (choice columns as labels), `conn.read(table, filter=..., limit=...)` and `conn.fetch(fetch_xml)` in Python. `%%sql Sales CRM` runs T-SQL on its read-only SQL endpoint (needs python-tds: no ODBC driver); when an admin has it off, the error says so and offers the `sab.read` line. For you: `connections_types` (the `dataverse` form), `connections_test`, `connections_create`, `connections_open_table`, `catalog_tables` |
| How do I build a Streamlit app from my data? | In the Workbench, **New app** opens a canvas (a tab, its own `.stapp.json` file). Write Python cells in a notebook (one that calls `st.` shows live in its cell; open tables are DataFrames by name), then drag a cell onto the canvas by its number (or from the canvas's Streamlit cells panel, by its name), or copy it (C) and paste (Ctrl+V): a block that links to the cell, on a 12-column grid. A Markdown or HTML cell goes on too (marked T; `st.markdown` or `st.html` on the page): its `{{ names }}` are reads, so a filter drives its text, escaped as text by the HTML cells' rules. A Markdown cell's ```mermaid block is drawn as a diagram in the notebook (a code block on a Streamlit page). **Play** shows the page live in place, **Edit** goes back; a cell that makes a name (`region = st.selectbox(...)`) drives the blocks that read it. **Export** writes a folder that runs alone; **Save as zip** zips the project (`data.py`, `pages/*.py`). A project starts with `data.ipynb` (New project… in a group's + menu). For you: `workbench_new_app`, `workbench_canvas`, `streamlit_block_place`, `streamlit_block_change`, `workbench_canvas_play`, `streamlit_save`, `streamlit_save_as`, `project_new`, `workbench_cell_name`, `streamlit_cells`, `workbench_pop_out`. `streamlit_export` waits for the user's Allow (it copies the tables' rows), as `table_export` does; `project_new` and `streamlit_save_as` too when data.ipynb would hold a pasted table's rows |
| How do I save my work and open it on another computer? | **Projects: a folder** in the guide: a project is a folder (its notebooks, scripts and apps as files; the app's state in a hidden .sab folder), so it can be a Git repository and shared like one. The home page is the **Project Explorer**: every project as a card (sortable, a custom order by dragging, the types explained for beginners). **New project** (name, type, where), **Open project…** (a folder), **Save** (Ctrl+S; **Autosave** on by default), **Copy to…**. A pasted table keeps its rows only when ticked, in `.sab/data/` (Git-ignored). Passwords stay on each computer. For you: `projects_list`, `project_new`, `project_open`, `project_save`, `project_copy` (`guide(topic="projects")`) |
| Document my project / What is this project's architecture? / Onboard someone to it | **Export outline** (the project's group; the Workbench's project menu) writes ARCHITECTURE.md at the project's top and offers its download: eight sections every time (overview, data sources, data model with an ER diagram, transformations as DuckDB SQL, lineage, deliverables, running it, open issues), names and types only. For you: `project_outline` (the markdown), `project_outline(write=true)` (the file, as Export does) |
| How do I schedule a notebook? / Run it in an Azure Function / Export it as one script | The document's **…** menu: **Export as one Python script…** (one .py: `python <file>`, `--install` pips its REQUIREMENTS, `main()` for a timer trigger) or **Export as one notebook…** (one linear .ipynb for nbconvert or papermill). Its connections, key vault lookups (an Azure Key Vault by the function app's managed identity) and grid steps are written out; no passwords, no rows, no Swiss Army Bench. For you: `workbench_export_script(path, format="script" or "notebook")`; what cannot be exported comes back in `problems`, and `stub: true` writes the rest with FILL IN stubs |
| Does my page work for every filter value? / A filter's defaults / This cell does too much | A cell's header line `# Makes: region: str = "All"; by_region: table = orders` is its **contract**: a block whose filter is not on the page reads those defaults (said quietly on the block). **Test this page** (beside Play) runs Streamlit's own test runner with each filter's values and turns the blocks that fail red with the value that broke them. A view that filters, groups or joins a table shows **Move to data.ipynb**: those lines become a named cell of data.ipynb and the view reads them back (`from data import ...`). For you: `streamlit_app` (each block's `controller`, `defaults`, `failures`, `thin`), `streamlit_check`, `streamlit_test`, `workbench_canvas_move_to_data` |
| Where does this value come from? / Check a notebook's results | Right-click a canvas block or a cell and choose **Lineage**: the flow back to the data as a chart, a card per step with its value (a table's rows, first rows and row change; a value; an error in red), live while the app plays. Right-click an output, **Approve the output**: a later run that differs says "Changed since approved" in amber; `python -m swissarmybench.client.standalone x.ipynb --check-approved` checks without the app (exit 1 and a report). For you: `workbench_lineage` (the flow, its Mermaid and each value), `workbench_lineage_show`, `workbench_cell_approve`, `workbench_approvals`, `workbench_approval_check` |
| How do I call a web API (an Azure Function, a Lambda, Firebase)? / Explore an API / Where did Add API go? | The rail's **APIs** page (its Add API: an OpenAPI document by address, file or paste, or the form; a sign-in type or a preset). The page explores them (search, inputs, outputs, schemas), **Author a call** sends one and opens the answer in **Structures**; **Return as table** on a web call makes it one of the API's tables (`SELECT * FROM list_orders` in `%%sql Orders`, `sab.read("Orders", "list_orders")`). ## Do not

- Don't approve your own export. The Allow click is theirs, and the server refuses an agent that
  tries.
- Don't ask for or print a password. Connections and blades read theirs from the keyring, an
  environment variable or a vault; set where one comes from with `connections_password_source`.
- Don't paste their table's values into the chat to "show" them something; open or filter the grid
  instead (`steps_put` or `steps_add`), so the data stays on their machine.
